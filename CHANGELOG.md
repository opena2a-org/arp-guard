# Changelog

This file starts at 0.4.0.

## 0.4.0

### Added

- Of the names a `require` of the package returns, 0.3.0 had 41 and 0.4.0 has 87: 0.4.0 re-exports every name the engine, `@opena2a/aim-sdk/arp`, exports, in place of a list of names, and adds `DEFAULT_MODEL_API_HOSTS`, the model API hosts AI-layer capture scans by default. None of the 41 is removed, nor any of the 36 types the declarations of 0.3.0 exported. The 46 names added are `ACTION_CLASSES`, `ClassificationAnnotator`, `CorrelationEngine`, `DEFAULT_MODEL_API_HOSTS`, `NanoMindGuardClassificationProvider`, `OUTCOME_CLASSES`, `RuntimeTwin`, `SIGNATURE_INGEST_PATH`, `SequenceLogWriter`, `SequenceProjector`, `SignatureEmitter`, `TACTIC_IDS`, `TARGET_CLASSES`, `TELEMETRY_SCHEMA_VERSION`, `appendAuditRecord`, `arpEventToLoggedAction`, `auditLogPath`, `behavioralHash`, `buildCanonical`, `buildSignedSubmission`, `canonicalShape`, `classifyTextHash`, `clearOptOutMarker`, `computeOrgPseudonym`, `currentOrgPseudonym`, `deriveOutcome`, `disclosureText`, `enrollSensor`, `eventToClassifyText`, `generateNonce`, `hasShownDisclosure`, `isTelemetryOptedOut`, `loadSensorId`, `manualEnrollCurl`, `manualPurgeCurl`, `maybeShowDisclosure`, `projectSequences`, `projectSequencesFromFile`, `purgeRemoteSignatures`, `readAuditRecords`, `readEnrollmentRecord`, `redactEvent`, `resolveTelemetryRegistryUrl`, `signatureTelemetryEnabled`, `toSignedResult` and `writeOptOutMarker`.
- The package ships `docs/`, `CHANGELOG.md` and `STATUS.md` beside the README and the license, so the README's links to them, and the links between the pages under `docs/`, name files an install holds. `test/package-files.test.mjs` checks each link from a page the package ships against the files `npm pack --dry-run` lists.
- With `aiLayer.prompt`, `aiLayer.mcp` or `aiLayer.a2a` enabled and `capture: true` set in it, `start()` passes the traffic the agent sends, and the model replies it reads, to the AI-layer interceptors. Before, it only marked them active and they scanned only what the application passed to them: an agent with all three enabled that sent a prompt injection to a model endpoint with `fetch` produced no event. The package's `AgentRuntimeProtection` extends the engine's class: `start()` hooks the global `fetch`, `request` and `get` of `http` and `https` and, with `aiLayer.mcp`, `spawn` of `child_process`, and `stop()` puts them back. The body of a request to a model API host goes to `scanInput` and its response to `scanOutput`; the hosts are `aiLayer.prompt.hosts`, by default the exported `DEFAULT_MODEL_API_HOSTS`. An event for a match in a reply carries `[masked: <n> characters]` in `data.matchedText` in place of the text the pattern matched, which for `OL-001` is a credential and for `OL-002` personal data. A JSON-RPC `tools/call` sent to any host, or written to the standard input of a spawned child, goes to `scanToolCall`, and an A2A `message/send`, `message/stream`, `tasks/send` or `tasks/sendSubscribe` request to `scanMessage`. Capture is off unless `capture: true` is set, and `enabled: true` alone keeps the interceptors as they were: capture runs them on the agent's thread, and for some texts the time some of the engine's patterns take grows faster than the length of the text, so a `tools/call` line with a 16 KB argument can hold the `write` that sends it for seconds. The AI-layer capture section of `docs/runtime-monitoring.md` says which requests and bodies are scanned and which are not, and why capture is off unless it is set, with an example and its output, and `test/ai-capture.test.mjs` checks them against the build.
- With `proxy` in the config, `start()` starts the engine's `ARPProxy` in the agent's process, listening on `127.0.0.1` alone, and `stop()` stops it; `getProxy()` returns it while it runs. Before, the engine read `proxy` nowhere: a request to its port was refused and nothing was scanned. The engine's own `ARPProxy.start()` listens on every interface. The proxy passes each request to the upstream whose `pathPrefix` it starts with and scans the request and the reply, by the upstream's `protocol`, with the interceptors `aiLayer` enables. What an output pattern matches in a reply is masked in the event, as with capture. When the proxy cannot listen, `start()` rejects with the error and leaves ARP stopped. With capture on as well, capture leaves a request the agent sends to the proxy's port at `localhost`, `127.0.0.1` or `0.0.0.0`, or at `127.0.0.1` or `0.0.0.0` as an IPv4-mapped IPv6 address, to the proxy, and does not scan the request the proxy sends to the upstream. The proxy does not scan a request it passes to a `passthrough` upstream, so capture scans that one itself, as sent to the upstream's `target`, and leaves its reply to the proxy; a `tools/call` with a `../../etc/hosts` path argument sent through such an upstream produced no event when capture left it to the proxy as well, and produces `MCP-001` now. The Proxy section of `docs/runtime-monitoring.md` says what each protocol scans, with an example and its output, and `test/proxy.test.mjs` checks them against the build.
- A `version` script in `package.json`, which `npm version` runs after it sets the new version, gives the `arp-guard` shim in `shim/arp-guard` that version, pins the shim's dependency on this package to it, and stages the shim's `package.json`, so the commit and tag `npm version` makes carry both. Before it, `npm version patch --no-git-tag-version` moved this package to 0.4.1 and left the shim at 0.4.0, and two checks in `test/shim.test.mjs`, which `npm test` runs, failed. Two tests there now make a bump in a scratch git repository and check the shim after it.
- AI-layer capture reports what it does not scan whole. A body it does not scan because it is larger than 1 MiB, and a scan whose result has `truncated: true`, as the engine, `@opena2a/aim-sdk` 1.3.1, gives for a text longer than the 65,536 characters it matches, each produce one event at `info` in the `normal` category, with `data.reason`, `body-over-limit` or `scan-truncated`, and the lengths, and none of the text. Before, neither produced an event: a request to a model API host whose prompt injection came after 70,000 characters of padding, or whose body was 1,048,681 bytes, left no event. A body larger than 1 MiB is reported from `prompt` for a model API host, and otherwise from `mcp-protocol`, or from `a2a-protocol` when MCP capture is off, with `data.bytes`, `data.limitBytes`, `data.direction` and `data.origin`, and a truncated scan from the interceptor that made it, with `data.contentLength` and `data.scannedLength`. The AI-layer capture section of `docs/runtime-monitoring.md` lists the fields, and `test/ai-capture.test.mjs` checks them against the build, with bodies of exactly 1 MiB and texts of exactly 65,536 characters as controls.

### Changed

- The package is renamed from `arp-guard` to `agent-runtime-protection`. Install `agent-runtime-protection` in place of `arp-guard` and change the import specifier. The rename changes no exported name and no API.
- The README is shortened to the install line, the first call and its output, the runtime-monitoring and AI-layer scanning examples, and links. Its reference text moved, as written, to `docs/install.md` (what the release on npm delivers, and the rename from `arp-guard`), `docs/runtime-monitoring.md` (the MCP and A2A interceptors, and which file operations the monitor reports), `docs/how-it-works.md` (the intelligence stack, the architecture, and the pattern count) and `docs/benchmark.md` (OASB).
- The README's longer paragraphs are split at sentence breaks into shorter ones. No text is added, removed or moved to another page.
- The README's Quick Start and AI-Layer Scanning examples pass `PATTERN_SETS.inputPatterns` to `scanText` in place of `ALL_PATTERNS`, and the Quick Start prints the same two lines. `ALL_PATTERNS` also holds the MCP and A2A patterns, which in ordinary prose report backtick spans, `../` and privilege words; the README now says which set is for which traffic.
- The README's AI-layer sentence says what the scanner is, 20 regular expressions in 7 categories, in place of a list of the attacks it detects.
- `docs/how-it-works.md` gives the figures measured against the DVAA attack corpus `attack-payloads.json`: how many of its entries `scanText` with the input set, the MCP interceptor and the A2A interceptor detect, and the command that measures them. `test/ai-layer-patterns.test.mjs` compares them with a fresh run when `ARP_DVAA_CORPUS` names the corpus file.
- The README no longer says process spawns are monitored without saying how. The process monitor polls `ps` every `monitors.process.intervalMs` milliseconds, 5000 by default, so a child process that starts and exits between two polls is not reported; the README and a new Process spawns section in `docs/runtime-monitoring.md` say so. That section shows the opt-in process interceptor (`interceptors: { process: { enabled: true } }`) reporting an `execSync` call when it is made, with the output of the example, and says that a reference to a `child_process` function taken before `start()` is not hooked.
- `docs/runtime-monitoring.md` has a Default rules section: the seven rules a config with no `rules` gets, what each matches, the action it takes, and what that comes to at each severity. It says that a `kill` triggered by a prompt, MCP or A2A event finds no process id and is logged as failed, as the one for PI-001 in the README's interceptor example is, and that `new AgentRuntimeProtection()` runs no rules unless the config file it finds sets them. The README says what the default rules do with that example's two matches and links the section.
- `docs/runtime-monitoring.md` has a Files ARP writes section: the data directory, which the constructor creates before `start()`, and the files ARP writes there; the behavioral twin's `events.jsonl` and `l1-escalations.jsonl` under `.opena2a/arp` in the home directory, with the fields of an `events.jsonl` line; and the two settings that turn the twin off. The README names both places and links the section.
- The Files ARP writes section of `docs/runtime-monitoring.md` names the files the two logs in the data directory are renamed to. When ARP has a line for `events.jsonl` or `enforcement.jsonl` and the file is larger than 50 MiB (52428800 bytes), it renames the file to its name followed by a dot and the time in milliseconds, such as `events.jsonl.1760000000000`, and writes the line to a new file under the old name. The renamed files stay beside the new ones.
- The File operations section of `docs/runtime-monitoring.md` says that the filesystem interceptor also reports writes made through `writeFile`, `writeFileSync`, `appendFile`, `appendFileSync`, `mkdir` and `mkdirSync`, at `info`, at `high` for a path on its list of sensitive paths, and at `medium` for a path outside `interceptors.filesystem.allowedPaths` when that is set, and that it reports `unlink` and `unlinkSync` of a path on the list at `critical`.
- The README says that the exported `VERSION` is the version of the engine, `@opena2a/aim-sdk`, not of this package, and how to read this package's own version.
- `test/runtime-monitoring-page.test.mjs` checks what the Default rules, Files ARP writes and File operations sections say against probes run on the build.
- The README is shorter: its Documentation line for `docs/runtime-monitoring.md` gives the page's topics in 19 words in place of 28, and seven more of its paragraphs are split into shorter ones. No text moved to another page.
- The README installs and imports `arp-guard`, the name the release on npm is published under, in place of `agent-runtime-protection`, which has no release on npm, so the Quick Start's first command, `npm install agent-runtime-protection`, failed with a 404. The README's other examples, its `require('arp-guard/package.json')` and the Process spawns example in `docs/runtime-monitoring.md` use the same name. The README's Renamed from arp-guard section says what `main` names the package, in place of telling a reader to install `agent-runtime-protection`. `docs/install.md` gives a fresh install of 0.3.0 on 2026-10-17 printing the Quick Start's two lines from the block as it now reads. The tests that run the README's commands load `arp-guard` from a copy of the shim in `shim/arp-guard`, which loads the build.
- The Renamed from arp-guard section of `docs/install.md`, which the README links, says to install and import `arp-guard`, in place of telling a reader to install `agent-runtime-protection` and import it: that name has no release on npm, so the command failed with a 404, as the Quick Start's did. The section says what `package.json` and `shim/arp-guard` name the package on `main`, and a test checks that `docs/install.md` installs and imports `arp-guard` alone.
- `docs/install.md` gives the number of packages and the disk space a fresh install of 0.3.0 adds to `node_modules`, beside those of a tarball packed from `main`, and names `onnxruntime-node`, the dependency of 0.3.0 with an install script.
- `docs/benchmark.md` records an OASB run in place of saying none is recorded: on 2026-10-21, OASB 0.4.0 ran against `@opena2a/aim-sdk` 1.3.1, the engine `package.json` pins, and 221 of its 222 scenarios passed, 0 failed and 1, `E2E-003`, was skipped. The page gives the platform and the commands of that run, which replace the `arp-guard` in an OASB checkout with a build of this repository, and says that `npm ci` in a checkout of OASB 0.4.0 installs `arp-guard` 0.3.0, which loads the engine copy in `hackmyagent` 0.23.8. A test in `test/readme.test.mjs` checks that the recorded counts add up to the suite size the page states and that the engine version it names is the one `package.json` pins.
- The `engines` field in `package.json` reads `^20.19.0 || >=22.12.0` in place of `>=18.0.0`. The engine, `@opena2a/aim-sdk` 1.3.1, loads `@noble/ed25519`, an ES module, with `require()`. On 2026-10-21, a `require` of a build of this package, run in the `node` container image of each version, failed with `ERR_REQUIRE_ESM` on Node 18.20.8, 20.18.3, 21.7.3 and 22.11.0, which `>=18.0.0` admits, and loaded on 20.19.0, 20.20.2, 22.12.0, 22.23.3, 23.0.0, 24.22.0 and 26.12.0, which the new range admits. On Node 18.20.8, npm 10.8.2 installs a tarball packed with `>=18.0.0` with no `EBADENGINE` warning, and warns `EBADENGINE` for one packed with the new range, whose install it refuses under `--engine-strict`. `test/engines.test.mjs` checks that the field admits none of the first four versions and each of the other seven, and that the engine version `package.json` pins is the one they were measured with.
- The AI-layer capture section of `docs/runtime-monitoring.md` says that `<n>` in `[masked: <n> characters]` counts the matched text the engine keeps, at most its first 200 characters, in place of saying that it counts the characters the pattern matched. The engine, `@opena2a/aim-sdk` 1.3.1, keeps the first 200 characters of a longer match, so a model reply whose `OL-003` match is 368 characters long gives `[masked: 200 characters]`. `test/ai-capture.test.mjs` checks the count for matches of 199, 200, 201 and 368 characters against the build, and that the page states it.
- `docs/install.md` gives four ways the release on npm, 0.3.0, differs from `main`, in place of two. One of the two was the L2 default, which `main` has as well, and the page gives it in a paragraph after the list. The README's install line installs 0.3.0, and the page did not say that npm runs the `postinstall` script of `onnxruntime-node`, the model runtime 0.3.0 brings with the `hackmyagent` scanner, and then prints four `npm warn install-scripts` lines; that the install places six executables in `node_modules/.bin`, of which an install of `main` places three; or that `require('arp-guard')` on 0.3.0 returns 41 names, without `writeOptOutMarker` and `clearOptOutMarker`, so that its telemetry opt-out is `npx aim-arp telemetry opt-out` and not a library call. The package counts and `node_modules` sizes of the two installs, measured again on 2026-10-22, moved from the item on the dependency chain to the item on the install. `test/install-page.test.mjs` checks that the section names the script, the executables and the two functions, and that the count it gives is the number of items in its list. It also checks that a build of `main` leaves L2 on for a config with no `intelligence` block, and that L2 appears in no item of the list.
- AI-layer capture scans the user turn that an assistant prefill follows. Before, it took the user, tool and function turns after the last assistant turn, which in a request that ends with a prefill is the prefill itself, so it took none: an agent with prompt capture on that sent a prompt injection with `fetch`, in a user turn followed by an assistant turn, produced no event, and a later request, which carries a reply after that user turn, did not scan it either. Assistant turns at the end of a request are now a prefill, text the model continues its reply from, and the last assistant turn is the last one before them. A request that sends a reply back for the model to continue also ends with an assistant turn, so the turns between that reply and the assistant turn before it are scanned again. The AI-layer capture section of `docs/runtime-monitoring.md` says so, and `test/ai-capture.test.mjs` checks it against the build.
- The `a2a` line of the Proxy section of `docs/runtime-monitoring.md` says that the proxy applies `aiLayer.a2a.trustedAgents` to the body's `from`, and that capture reads no sender from the body: it scans the message as sent from the config's `agentName` and does not apply `trustedAgents`. With `trustedAgents: ['planner']`, a `message/send` body whose `from` is `stranger` gets an `A2A message from untrusted agent: stranger` event when the agent sends it through the proxy, and no such event when the agent sends it to the peer itself with `capture: true`. Before, the section did not say that the two differ. `test/proxy.test.mjs` sends that body both ways against the build, and checks that the page states what it measures.
- The README and `docs/runtime-monitoring.md` say what an AI-layer interceptor does on the published engine with a long text and before its own `start()`. It matches only the first 65,536 characters of the text it gets, and when there were more, the result of `scanInput`, `scanOutput` or `scanToolCall` has `truncated: true`, that of `scanMessage` has no `truncated` field, and the call emits no event that says so. A call before `start()` returns `{ detected: false, matches: [] }` and emits no event, and `isRunning()` returns `false` until then. The README, `docs/install.md` and `docs/runtime-monitoring.md` say that `arp.getRuntimeTwin()` returns `null` when the twin is off, and that a twin that is on means L2 is on as well, which checks that `intelligence: { enabled: false }` was read as off: on that engine, `enabled: "false"` leaves both on. The `passthrough` line of the Proxy section says that `scanOutput` matches only the first 65,536 characters of the reply. `test/runtime-monitoring-page.test.mjs` checks each against a probe run on the build.

### Deprecated

- `arp-guard` is deprecated in favour of `agent-runtime-protection`. For the transition, `arp-guard` 0.4.0 is a shim that depends on `agent-runtime-protection` 0.4.0 and re-exports it, so an install or a peer range that names `arp-guard` keeps working.
